# Pixel Hotspot Toggle — BLE protocol v1 (frozen)

Pixel = GATT peripheral (server), Mac = central (client).

## UUIDs

| Name | UUID | Properties | Security |
|------|------|------------|----------|
| service | `13f60001-33cc-47ff-8e19-0a93d1157c5b` | primary, advertised | — |
| `nonce` | `13f60002-33cc-47ff-8e19-0a93d1157c5b` | read | encrypted |
| `command` | `13f60003-33cc-47ff-8e19-0a93d1157c5b` | write with response | encrypted |
| `state` | `13f60004-33cc-47ff-8e19-0a93d1157c5b` | read, notify | encrypted |
| `pairing` | `13f60005-33cc-47ff-8e19-0a93d1157c5b` | read | encrypted |

"Encrypted" = the link must be encrypted with a bonded key. The first access
from an unbonded Mac triggers LE pairing (LE Secure Connections when both
sides support it; numeric comparison is shown on both screens).

Advertising: flags + the 128-bit service UUID, no name. Mode *balanced*
(~250 ms), connectable. Advertises all the time while the service runs.

## Pairing (one time)

1. On the phone the user taps **Pair Mac**. A 60 s pairing window opens.
2. On the Mac the user clicks **Pair…**. The Mac scans for the service UUID,
   connects and reads `pairing`. macOS and Android show the bonding dialog;
   the user confirms the same code on both.
3. While the window is open `pairing` returns the pairing record (CBOR map):

   | key | type | meaning |
   |-----|------|---------|
   | `k` | bstr(32) | shared secret for HMAC |
   | `s` | tstr | hotspot SSID |
   | `p` | tstr | hotspot passphrase (WPA2/WPA3-transition) |

   Outside the window, or after one successful read, it fails with ATT
   error `0x83`. The window closes after the first successful read.
4. The Mac stores `k`, `s`, `p` and the CoreBluetooth peripheral identifier
   in the Keychain. The phone keeps `k` encrypted with an Android Keystore key.

The secret, SSID and passphrase are generated by the phone on first start.
Changing SSID/passphrase on the phone requires pairing the Mac again.

## Commands

1. Read `nonce` → 16 random bytes.
2. Write `command` (49 bytes):

   ```
   op(1) ‖ nonce(16) ‖ HMAC-SHA256(k, op ‖ nonce)(32)
   ```

   | op | meaning |
   |----|---------|
   | `0x01` | ON — start Wi-Fi tethering with the paired SSID/passphrase |
   | `0x02` | OFF — stop Wi-Fi tethering (whoever started it) |
   | `0x03` | STATUS — refresh telemetry and notify `state` |

   The value may arrive as a single write or as a long (prepared) write.
3. The server regenerates `nonce` after **every** write to `command`,
   accepted or not. A nonce is therefore single-use; replayed or
   out-of-order frames fail.
4. Write response:

   | ATT status | meaning |
   |------------|---------|
   | `0x00` | accepted; the result shows up in `state` |
   | `0x80` | rejected: wrong length, stale nonce or bad HMAC (not distinguished) |
   | `0x81` | unknown op (HMAC was valid) |
   | `0x82` | ON/OFF impossible: Shizuku not running or no permission |

   HMAC comparison is constant-time.

## State

`state` holds one CBOR map (≤ 512 bytes). A notification carries the same
bytes; when the value is longer than ATT_MTU − 3 the notification carries
an empty value and the Mac reads the characteristic (long read).
The server notifies on every change.

| key | type | meaning |
|-----|------|---------|
| `v` | uint | protocol version, `1` |
| `hs` | uint | hotspot: 0 off, 1 starting, 2 on, 3 stopping, 4 error |
| `err` | int | error code, present only when `hs = 4` (tethering error code; `-1` = AP failed) |
| `ssid` | tstr | SSID of the running hotspot, present when `hs = 2` |
| `cl` | array | clients: map `{mac: tstr, ip?: tstr, n?: tstr}` (hostname `n`) |
| `ncl` | uint | total number of clients (`cl` may be cut to fit 512 bytes) |
| `bat` | uint | battery % 0–100 |
| `chg` | bool | charging |
| `net` | uint | cellular: 0 none, 1 3G (or older), 2 LTE, 3 5G NSA, 4 5G SA |
| `sig` | uint | signal level 0–4 |
| `shz` | uint | Shizuku: 0 ok, 1 not running, 2 no permission |

Readers must ignore unknown keys.

## Hotspot state machine (phone)

```
            ON cmd                AP ENABLED
   off ───────────────► starting ───────────► on
    ▲                      │                  │
    │ AP DISABLED          │ start failed     │ OFF cmd / AP DISABLING
    │                      ▼                  ▼
    └──────────────────── error        stopping ──► off (AP DISABLED)
```

Transitions come from the system (`WIFI_AP_STATE_CHANGED`, tethering
callbacks), never from the fact that a command was sent. Changes made on the
phone itself (quick settings) follow the same path. `error` holds until the
next command or the next AP state change.

## Mac flows

- **ON:** connect (if needed) → read `nonce` → write ON → wait for
  `hs = 2` (timeout 15 s) → join Wi-Fi `s`/`p` unless already on `s`.
- **OFF:** read `nonce` → write OFF → leave Wi-Fi `s` if joined.
- The Mac stays connected and subscribed to `state` while the phone is in
  range and reconnects automatically.
